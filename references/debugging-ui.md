# 界面排错

改动看着不对时，**先量，再改**。这一篇只管一件事：把「我觉得哪里不对」
变成一个能测的数，然后改到测过为止。

排错最贵的成本不是改，是猜。凭 CSS 语义猜出来的原因，
看着像那么回事，修完不对，还得再来一轮。

## 三条纪律

1. **先量后改**。改之前必须有一个测得的数（宽度、对比度、坐标、属性值）。
   没有数支撑的「修复」，只是把一个未知换成了另一个未知。
2. **一次只改一处**。同时改三处再看效果，好了不知道是哪处起作用，
   没好更不知道该回退哪处。
3. **改完立刻复测同一个数**。不测就等于没改。

## 探针脚本：一次问清 computed style 和盒模型

页面上挂一小段脚本，把怀疑对象的真实状态打印出来。这是排错的默认手段，
优先于读源码猜测。

```js
(function () {
  var el = document.querySelector('.怀疑的元素');
  var cs = getComputedStyle(el);
  var r = el.getBoundingClientRect();
  var out = {
    rect: { w: r.width, h: r.height, x: r.x, y: r.y },
    display: cs.display,
    flex: cs.flex,
    minWidth: cs.minWidth,
    width: cs.width,
    overflow: cs.overflow,
    whiteSpace: cs.whiteSpace,
    // 关键：子项也量一遍，塌缩往往发生在子项
    children: [].slice.call(el.children).map(function (c) {
      var b = c.getBoundingClientRect();
      return { cls: c.className, w: b.width, flex: getComputedStyle(c).flex };
    })
  };
  console.log('PROBE ' + JSON.stringify(out));
})();
```

把这段临时插进页面（记得配 `<script>` 标签，见案例三），从控制台读输出，
或让 `shoot.mjs` 的 `report.json` 收走。**量到子项**是关键：
父容器看起来正常时，塌缩往往发生在子项上。

量完删掉探针，别留在交付物里。

## 案例一：overflow hidden 容器里 flex 子项宽度塌缩

**现象**：一段日志/标签文本在窄容器里每个词单独占一行，容器宽 400px 而
内容区只剩 130px。

**猜错的五轮**：把 `display:block` 改成 `grid` 再改 `flex`、把 `<pre>` 换成
`<div>`、加 `white-space:pre`、给唯一子元素加 `grid-column:2`、
换文件名规避缓存。全部无效。

**测出来的事实**：内容列 `.m` 的 `getBoundingClientRect().width` 是 **0**。

**根因**：在 `overflow:hidden` 的 flex 容器里，没有显式 `flex-grow` 的子项
**不按内容宽度分配，而是塌缩到内容最小宽度**——一行放不下就退到逐词换行。
「一行一行」不是换行规则的问题，是宽度为 0 的问题。

**修法**：给内容列显式宽度和溢出处理。

```css
.row { display: flex; align-items: baseline; white-space: nowrap; }
.row > .固定列 { flex: 0 0 9.5em; }
.row > .内容列 { flex: 1 1 auto; min-width: 0; overflow: hidden; text-overflow: ellipsis; }
```

三个零件缺一不可：`flex: 1 1 auto` 给宽度、`min-width: 0` 允许收缩到内容以下、
`overflow: hidden` 裁掉超长内容。

**推广**：任何 `overflow:hidden` 的 flex 行，宽度相关的子项都要显式声明 flex。

### 附：底部留白是同一个原理的另一面

「内容挤在顶部、下面一大片空白」看着像间距问题，实际是**等高单元格里
内容量不等的必然结果**。三列并排、每列两行字、容器被最高的那列拉高，
其余两列的底部就空了。

**不要靠调 padding 补**，那只会把空白挪个位置。正确做法是让短的那一列
自己把内容推到视觉底边：

```css
.cell { display: flex; flex-direction: column; }
.cell__note { margin-top: auto; }   /* 底部备注贴底 */
```

一行 flex 列布局就解决了，而且**多列的底边会自动对齐成一条基线**——
这是额外收益，比「每列高度差不多」更好。
`.cell__note` 上加一条 `border-top` 分隔线，效果更清楚。

## 案例二：文字重叠成一团——pin 钉错了对象

**现象**：滚动时首屏的标题和下一节正文叠在同一位置，糊成一团。

**根因**：`pin: '.hero__screen'` 钉的是 `.hero` 内部的子元素。pin 高度按被钉
元素算，但滚动距离是按触发元素算的，两者不一致时，下一节会在 pin 还没结束
时就滚上来。

**修法**：`pin: true` 钉住触发元素本身，让高度和滚动距离同源。

```js
gsap.timeline({
  scrollTrigger: {
    trigger: '.hero', start: 'top top', end: '+=70%',
    scrub: 1, pin: true, pinSpacing: true, anticipatePin: 1
  }
})
```

`pinSpacing: true` 让钉住期间占住文档流高度，`.hero` 在钉住期间高度撑开，
这段滚动距离就是它撑开的高度。`end` 的百分比要覆盖 pin 期的缩放幅度，
缩放幅度越大距离越长；改完量一下相邻两节有没有还在 pin 期就重叠。

## 案例三：点击无反应——脚本从来没执行过

**现象**：加的明暗切换按钮点了没反应。视觉上滑块还动了，提示文字也变了，
但 `document.documentElement.getAttribute('data-theme')` 是 `null`——
**处理器从未执行**。

**根因**：脚本块被放在了 `</footer>` 之后、**任何 `<script>` 标签之外**。
裸的 `function(){...}` 在 HTML 里是文本节点，浏览器只当文字渲染，不执行。
用脚本批量插入 HTML 时很容易踩到：插入点落在了标签外。

**排查顺序**：先用探针确认 `getAttribute('data-theme')` 是不是 null。

- 属性是 null → 脚本没执行。查它是不是在标签外（`grep -c '<script'` 对比块数）
- 属性有值但不更新 → 事件没绑上。查绑定时机和选择器是否命中
- 属性更新了但画面没变 → 查样式层：令牌有没有被更高优先级规则覆盖

**顺带一条**：影响首屏外观的脚本（例如读 localStorage 定主题，防白屏闪烁）
必须放在 `<head>` 内、样式和内容之前。放在 `</body>` 前再正确，也会先闪一下
错误主题。判断归属时按**它影响什么**来放，不按它在源码里的位置。

## 案例四：截图里的对比度「不达标」是动画中途取样

**现象**：工具报 12 处文字对比度 4.4:1，不达标。但对应色值单独算出来是
7.28:1，远高于标准。

**识别方法**：4.47 ÷ 7.28 ≈ 0.61，是个有意义的比例——这是**透明度中途值**，
不是色值问题。入场动画把元素从 `opacity:0` 推到 1，截图恰好在中间取样。

**修法**：截图前等动画播完。

```bash
node scripts/shoot.mjs <页面> --wait 2400 --out <证据目录>
```

`--wait` 默认只有 400ms，对入场动画偏短。**有出场动画、有 `--wait 校准`
要量的页面，一律显式给 `--wait 2000` 以上。**

**别做的事**：为了让报告变绿去改本来达标的色值。

### 滚动之后再截：错峰动画是第二个坑

上面是首屏入场动画。**滚动到页面中段再截，会撞上第二个更隐蔽的坑**：
区块出场动画由滚动触发，`scroll` 动作一执行动画就开始播，截图立刻落下——
落在哪一帧完全取决于 `stagger` 有多长。

实测：5 行列表用 `stagger: .07`，最后一行要等 0.28s 才开始播。
截图落在 `opacity=0.205` 的那一行，肉眼看就是「整行淡得几乎看不见」，
工具同时报出 33 处对比度不达标、最低 1.50:1。

**识别方法**（三条同时成立基本可判定）：

1. 同一份代码报出两处不同的对比度——同一份 CSS 不可能同时有两个对比度。
2. 报出的示例元素**此刻不在视口内**（已滚过去了）。
3. 视觉上元素是「淡的」而不是「颜色不对的」，色相没变只是发灰。

**修法一（取证用）**：滚动后显式等一段，让动画播完再截。

```bash
--steps "scroll 1700;wait 1400"
```

这一步是**取证正确性的前提**，不是可选项。看到大片元素发淡先加 `wait` 复测，
加完还淡才是真问题。

**修法二（页面本身用）**：错峰别太长。列表类 5 条以上时，
`stagger` 压到 `.045` 以内、`duration` 压到 `.45` 以内、触发点提前到 `88%`。
过长错峰的真实代价是：用户滚过去要等半秒才看完，不只是截图难看。

**两者的分工**：取证时靠 `wait` 拿到真实画面；页面体验靠压参数。
不要用 `wait` 掩盖一个本来就过长的错峰——那会让动画问题一直留在页面上。

## 案例五：截图工具连不上，看到页面

**现象**：把文件当 URL 传给截图工具，页面打不开或工具直接失败。

**根因**：部分浏览器把端口 6000–6699 列为**不安全端口**（含 6697），
出于防 CSRF 的历史约定会直接拒绝连接。

**修法**：文件名加下划线前缀，规避端口冲突与工具的历史限制。

```bash
cp 页面.html _preview.html
node scripts/shoot.mjs <目录>/_preview.html --out <证据目录>
```

证据目录可以是临时目录，验完删掉；`_` 前缀的文件不要留在交付目录里。

**另一个环境坑**：Windows 上用 curl 抓外部资源报
`CRYPT_E_REVOCATION_OFFLINE`（证书吊销检查拿不到网络）。加
`--ssl-no-revoke` 能解决。下载字体、样式这类外部资源时都可能撞上。

## 误报怎么处置

工具会误报，分两种，处理方式不同：

- **工具判断不了意图的**（真实步骤编号、确实需要的标签、卡片里确实该套一层）：
  保留，在交付说明里写一句为什么这么定。不要为了变绿去改。
- **取样时机/背景识别导致的**（对比度受动画透明度影响、背景没查准、
  工具不报但自己看截图能看出的）：先确认成因，再决定是加等待、换取样点，
  还是真的不合格。

**同一批报告里出现「同一处色值一次说 4.4:1、一次说 7.28:1」，
先怀疑取样时机，再怀疑色值。** 同一份代码不可能同时有两个对比度。
