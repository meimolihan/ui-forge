# 存量项目改造

新项目可以从零定；存量项目只能改。这篇讲**在既有代码上改界面**的顺序和风险。

核心原则：**从源头修，不为一次调整另造系统。**
为了一个圆角角引入一套新框架，是把视觉工作变成重构，风险和收益完全不成比例。

---

## 一、先分清用户要哪一种

三种诉求做法完全不同，**问清楚或从上下文判断，但要说出来**：

| 用户说 | 实际诉求 | 能动什么 |
| --- | --- | --- |
| 「界面太丑，优化一下」 | **视觉** | 重新决定偶然形成的视觉默认值，保留品牌资产 |
| 「流程太绕，改一下」 | **流程** | 沿用现有视觉，改操作步骤和信息顺序 |
| 「加个 XX 功能」 | **新功能** | 沿用现有视觉，新增部分照既有模式做 |

**混着做会两头不讨好。** 改流程时顺手重画视觉，用户会不适应；
纯改视觉时调整了操作顺序，功能逻辑可能已经坏了。

**品牌资产保留**：logo、品牌色（如果用户认得这个色）、文案语气、
已经定好的设计系统。不保留的是：某次赶工留下的魔法数字、
互相打架的三套间距、不知道从哪来的一个 `#1a1a2e`。

---

## 二、盘点：只读相关的

不先通读整个项目。按这几项定位，每个都有明确的查法：

| 查什么 | 怎么查 |
| --- | --- |
| 设计变量在哪 | `grep -nE "\-\-[a-z-]+:" 文件` |
| 有几套覆盖层 | `grep -c "<style>" 和 "^\s*\.类名\s*{"` |
| 表格/卡片是不是组件化 | 搜重复的 DOM 结构 |
| 断点在哪 | `grep -n "@media"` |
| 项目能不能构建 | 先跑一次构建 |

**先确认能不能构建。** 构建不了的项目只能做静态分析，
你无法验证任何改动，风险成倍上升。本 Skill 遇到过用
`syscall.Setpgid`（Linux-only）的 Go 项目在 Windows 上完全无法构建——
这种情况下诚实说明「未验证实际运行」，不要假装改好了。

---

## 三、留基线

改之前先截一张。**没有基线就看不出改动是变好还是变坏**，
也说不清哪些是原有的问题。

```bash
node scripts/shoot.mjs <页面> --out baseline/
```

基线至少要：默认状态 + 一个有数据的状态 + 手机视口 + 深浅两主题。
缺了基线，后面对比只能靠记忆。

---

## 四、查规则，找系统性问题

这一步是存量项目**最容易被跳过、也最值钱**的一步。

老项目的问题往往不是「某个控件不好看」，而是**系统性的规则缺口**：
所有输入框都 `outline:none`、所有 tag 颜色都没过对比度、
所有按钮都小于触控尺寸。这类问题逐个看发现不了，得先查。

```bash
python scripts/search.py "focus visible keyboard" --domain ux
python scripts/search.py "color alone convey meaning" --domain ux
python scripts/search.py "target size minimum" --domain ux
python scripts/search.py "touch target spacing" --domain ux
```

一次查询拿到的是「有数字标准的要求」，比「看着有点小」可靠得多。

**清单式排查**（把 119 条规则按项目类型过一遍，比凭印象想更全）：

```
可访问性 → 焦点可见、颜色对比、颜色非唯一语义、标签关联
交互 → 六态齐全、loading 不变形、禁用有理由
布局 → 无横向溢出、密度是否够、响应式断点
动效 → reduced-motion、时长、退出比进入快
```

---

## 五、分批改，别一次改完

**一批改一个主题，改完就验证。** 一次改二十处，出问题时你分不清是哪处引起的。

批次的划法：

1. **可读性批**：对比度、焦点环、字号行高 —— 纯视觉，零风险，先做
2. **布局批**：溢出、列宽、密度 —— 中等风险
3. **层级批**：视觉权重、减法 —— 需要看图判断
4. **动效批**：状态反馈、过渡 —— 最后做，因为最容易掩盖前面的问题

每批之间**重新截图**。不要攒到最后。

---

## 六、改的顺序：变量 → 组件 → 页面

改的落点决定改动能不能传播：

```
设计变量（--primary, 间距, 圆角）  ← 改一次，全站生效
  ↓
共享组件样式（.btn, .tag, .stat-card）  ← 改一次，多页生效
  ↓
页面级样式（.stats-grid, #panelCron）  ← 只影响本页
  ↓
行内 / 具体元素  ← 最后手段
```

**从上往下改。** 底层改一次能解决上层十个问题；
从行内开始改会留下一堆互相打架的覆盖规则。

**新样式集中追加在样式表末尾**，附注释说明改了什么、为什么。
不改动既有规则——你无法确定改动的调用方，后者比重新设计更贵。

---

## 七、层叠陷阱（老项目高发）

改动既有样式表时最容易翻车的地方：

**用 `:where()` 会被原有规则盖掉。** `:where()` 特异性为 0，
压不过项目里的 `.toolbar input{outline:none}`。
结果是「我加了焦点环，怎么更看不见了」。特异性不够时用带类名的选择器。

**`opacity` 会把文字和底色一起混算。** 想让辅助文字弱一点，
不要用 `opacity: 0.9`——它的计算对比度可能反而掉到标准以下
（实测掉到 3.55:1）。改为直接指定一个仍然达标的颜色值。

**不依赖列序写选择器。** 老项目常有多个表格（不同页签，列数不同）。
`nth-child(5)` 在另一张表上指的不是同一列。
用 `first-child` / `last-child` 或语义化的类名。

**追加覆盖层时先看它之前有没有同名规则。** 同名规则谁生效取决于顺序，
不取决于你想的。改完必须实测——本 Skill 遇到过两次「CSS 写对了但没生效」。

---

## 八、验证

### 看不见的东西必须实测

对比度、焦点环、层叠覆盖这些，**看代码判断不了**。

```bash
node scripts/verify_focus.mjs <页面>      # 焦点环：真实 Tab 实测
node scripts/shoot.mjs <页面> --evidence  # 对比度、溢出、动效
```

`:focus-visible` 只在真实键盘导航时匹配，用 `element.focus()` 验证会得到
**不稳定且错误**的结果。用 `verify_focus.mjs`，它派发真实 Tab 键。

### 逐项对照改了什么

每改一处，对照基线看三件事：改动处、相邻元素、有没有连带影响。
共享样式改了会影响所有用到它的页面——这种改动要重新取全站证据。

### 如实说没验证什么

构建不了、连不上后端、无法交互验证时，**在交付说明里写明**。
「未在真实环境验证交互」比含糊的「已优化」有价值得多。

---

## 九、交付说明写什么

存量改造的交付说明要回答这几个问题：

- 盘点了什么，改了哪些文件
- 基线在哪，改动后在哪，前后能对比
- **查了规则库的哪几条，命中没有**（没命中要说明，不能装作查过）
- 哪些改动做了取舍，为什么
- **哪些没验证、为什么没验证**
- 有没有发现但没改的问题，为什么留着
