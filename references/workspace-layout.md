# 后台与工作区

后台不是「把组件摆上去」，是**让一个每天要用它的人，用最少的眼动完成工作**。
用户来后台不是为了看界面，是来看**有没有问题**、**有什么要处理**。

这篇管：怎么按产品性质挑工作区布局、怎么排信息层级、后台特有的密度问题。

---

## 一、先定用户来干什么

同一个「仪表盘」，用途不同，布局完全不同。动手前回答一句话：
**用户打开这个页面，第一个动作是什么？**

| 用户的动作 | 该用 | 为什么 |
| --- | --- | --- |
| 发现有问题就去处理 | **异常优先**布局 | 正常状态折叠起来，出错的顶上来 |
| 定期看一眼趋势 | **指标 + 趋势**布局 | 关键是时间维度，要能比较 |
| 直接找一条记录 | **列表优先**布局 | 一行就是一条，搜索和筛选是主角 |
| 对比多个对象 | **主从/分栏**布局 | 需要同时看到列表和详情 |

对应规则库里 dashboard 布局的分类，检索：

```bash
python scripts/search.py "realtime monitoring dashboard" --domain product
python scripts/search.py "ops console" --design-system --density 8 -p "Ops"
```

`--density 8–10` 给后台（8–32px 间距尺度），落地页用 `--density 1–3`（24–96px）。
后台挤一点是功能性的：同样一屏能看到更多行，日常操作效率更高。

## 二、后台的骨架

多数后台可以套这个骨架，按需要增删，不要另起一套：

```
┌─────────────────────────────────────────┐
│ 顶栏：产品名 / 全局搜索 / 账号 · 通知│  ← 固定，全局动作
├──────┬──────────────────────────────────┤
│ 侧栏 │ 页头：标题 + 主操作按钮            │  ← 每页重复
│ 导航 │──────────────────────────────────│
│      │ 状态区：4 个关键指标（一行）       │  ← 只放需要扫的
│      │──────────────────────────────────│
│      │ 内容区：表格 / 图表 / 表单        │  ← 主角，占最大
│      │──────────────────────────────────│
│      │ 分页 / 批量操作栏                 │
└──────┴──────────────────────────────────┘
```

**状态区只放需要扫的**，不是所有数字。四个是上限——超过四个就没人看了，
用户会略过整排。选择标准：这一项异常时，用户需不需要立刻知道？
需要，就放；不需要，去详情页看。

每张状态卡的**数字要有说法**。孤零零一个「7」没人知道好坏：

```
7 任务总数              ← 不合格
7 个任务 · 2 个失败     ← 合格
```

对比规则：规则库给了明确数字标准时先查再定。

```bash
python scripts/search.py "stat card metric clarity" --domain ux
```

## 三、表格：后台的主战场

后台一半的时间花在表格上。四件事决定它好不好用。

### 1. 一眼找到异常

后台表格的用途是**筛出该处理的**。三个手法：

- **状态用文字 + 颜色双通道**，不能只有颜色（`Color Only` 反模式）。
  规则库：`search.py "color alone convey meaning" --domain ux`。
- **异常行排序到前面**，而不是让用户自己找。执行中的、失败的排在最前。
- **异常行给一个视觉锚点**（左侧状态条、淡色底），扫一眼就能定位。
  别用会在行上移动的高亮——动效让「找行」变成「盯着看」。

### 2. 主操作靠近行，破坏性远离行

一行的操作按钮按**后果轻重**排，也按**位置**分：

```
执行  编辑  记录 │ 删除
 └─高频无害 ─┘   └─ 低频危险 ┘
```

破坏性按钮**不要紧挨**高频按钮：密集排列时误点代价高。要么隔开并用 danger 色，
要么把破坏性操作收进「更多」菜单。

**每个按钮的触控区域**：桌面端 ≥24×24px（WCAG 2.2 AA），相邻间距留够。
密集表格里最容易忽略的是按钮间距——尺寸达标但挤在一起，误点率照样高。

### 3. 别把关键信息压缩掉

表格横向空间不够时，压缩顺序是：

1. **先压辅助信息**（相对时间、次要标签）
2. **再压名称**（用省略号，hover 出完整值）
3. **再压间距**（padding 从 12px 到 9px）
4. **最后才横向滚动**

**不要压的一类：判断依据。** 比如计划任务的 cron 表达式、金额、状态。
看错一次就可能误判影响，这类内容宁可换行也要完整。

压缩时避免用 `:where()` 写覆盖规则（见
[交互与状态](interaction-states.md) 的焦点环一节，同一个坑）。

### 4. 空态与筛选态分开

筛选后没结果 ≠ 真的没有。两种空态文案不同：

```
真没有：  还没有任务     [新建任务]
筛没了：  没有匹配「备份」的结果   [清除筛选]
```

混为一谈会让用户以为数据丢了。

## 四、后台的密度取舍

后台挤是功能性的，但有三处不该挤：

| 位置 | 建议 | 原因 |
| --- | --- | --- |
| 表格行内操作按钮 | ≥24px，可到 32px | 误点代价高 |
| 表单输入框 | ≥36px，移动端 ≥44px | 输入精度 |
| 正文与标签文字 | ≥13px，行高 1.5 | 中文小字号可读性差 |
| 卡片内边距 | ≥12px | 挤在一起分不清分组 |

**中文界面尤其别用小字**。规则库把「正文字号 < 13px」列为
`Typography` 类反模式，中文笔画密度高，比拉丁字母更早失去可读性。

## 五、移动端后台

后台的移动端场景通常是**查看 + 应急处置**，不是完整办公。

- **表格转卡片**：不是把表格横向滚动塞进手机，是每行变一张卡。
  规则库：`search.py "data table mobile" --domain ux`。
- **主动作收成固定底栏**：拇指区。不是把按钮浮在内容上。
- **次要列在卡片里降级**：一行 8 列变卡片后，只留 2–3 个关键字段 + 一个「详情」。

**别在移动端堆功能。** 桌面端有 10 个操作，移动端给 3 个最常用的，
其余进「更多」。

---

## 六、把风格贯穿整页

后台的「风格」不在卡片长什么样，在**节奏**是否一致：同一个间距尺度、
同一套状态色语义、同一种边框和圆角。规则库有主题一致性条目：

```bash
python scripts/search.py "design system consistency tokens" --domain ux
```

具体做法：

1. **先立变量再写样式**。间距、字号、圆角各定 8–12 个值，组件只引用变量。
2. **状态色是语义 token 不是颜色值**。`--success` / `--danger` / `--warning`
   表状态，不是「绿色」/「红色」。深浅主题各自给一套值，同一语义。
3. **对比度要两种主题分别验**。浅色主题的饱和色在白底上常常不达标
   （常见的是绿、蓝），别只验深色。

## 自查

- [ ] 说得出用户打开这个页面的第一个动作，布局是为它服务的
- [ ] 状态区不超过 4 项，每项数字都带上下文说明
- [ ] 表格异常行能一眼定位，状态不只靠颜色
- [ ] 破坏性操作与高频操作隔开
- [ ] 压缩表格时判断依据类信息（金额、频率、时间）没被压掉
- [ ] 「筛选后无结果」和「真的没有」文案不同
- [ ] 触控目标 ≥24px 且间距足够
- [ ] 深浅两种主题的对比度都验过
- [ ] 移动端是卡片布局，不是横向滚动的表格
