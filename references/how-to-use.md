# 使用手册

两件事：**优化现有项目的 UI**、**从零做一个新项目**。
两件事的入口不同，流程不同，但判断层和规则层是同一套。

| 场景 | 从哪读起 | 核心差别 |
| --- | --- | --- |
| 优化现有 UI | [存量改造](legacy-refactor.md) | 不能从零定，只能改；必须先留基线 |
| 创建新项目 | [设计方向](design-direction.md) | 方向未定，要先探索再落地 |

---

## 一、准备工作

只有三件事，一次做完就不用再管。

**1. 确认项目能跑起来。** 这是两条路的共同前提。跑不起来就只能做静态
分析，改动无法验证——交付时必须写「未验证实际运行」。

```bash
# 按项目实际技术栈选一条
npm run dev            # / pnpm dev / yarn dev
python manage.py runserver
flutter run
go run ./
```

跑不起来先查是不是环境问题（缺依赖、端口被占、跨平台）。
确实是平台限制（比如项目用了 `syscall.Setpgid` 这类 Linux-only 调用），
就转用静态分析路线，并在交付说明里写清楚。

**2. 检测技术栈。** 规则库能按栈给实现提示，猜错栈会让每条建议都跑偏。

```bash
ls package.json pubspec.yaml *.xcodeproj build.gradle 2>/dev/null
```

**3. 准备工作目录。** 截图、对比页、设计说明、评审记录全放这里，
**不要写进 Skill 安装目录**。

```
<任务目录>/
├── baseline/     改动前的截图
├── evidence/     改动后的取证
├── candidates/   新项目时的方向小样
└── DELIVERY.md   交付说明
```

## 二、优化现有 UI

完整方法读 [存量改造](legacy-refactor.md)，这里是可以照着敲的流程。

### 步骤 1：说清诉求

用户说「界面太丑，优化一下」，实际可能是三件事之一，做法完全不同：

| 用户说 | 实际诉求 | 能动什么 |
| --- | --- | --- |
| 界面太丑，优化一下 | **视觉** | 重新决定偶然形成的视觉默认值，品牌资产保留 |
| 流程太绕，改一下 | **流程** | 沿用现有视觉，改操作步骤和信息顺序 |
| 加个 XX 功能 | **新功能** | 沿用现有视觉，新增部分照既有模式做 |

混着做两头不讨好。判断完直接告诉用户你的理解。

### 步骤 2：查规则库（最容易跳过，也最值钱）

老项目的问题几乎都是**系统性的规则缺口**，不是「某个控件不好看」：
所有输入框都 `outline:none`、所有 tag 色都没过对比度、所有按钮都小于触控尺寸。
这类问题逐个看发现不了。

```bash
python scripts/search.py "focus visible keyboard"        --domain ux
python scripts/search.py "color alone convey meaning"   --domain ux
python scripts/search.py "target size minimum"          --domain ux
python scripts/search.py "data table dense scanning"    --domain ux
python scripts/search.py "modal dialog"                 --domain ux
python scripts/search.py "<技术栈关键词>" --stack <stack>
```

先把要查的清单列出来再逐条查。查不到就如实说「规则库无匹配」，
退回通用默认值并标注这是默认值——**不要拿常识冒充数据库命中**。

### 步骤 3：留基线

没有基线就看不出改动是变好还是变坏，也说不清哪些问题是原有的。

```bash
node scripts/shoot.mjs <页面地址> --size desktop,390x844 --out baseline/
```

至少要四张：默认状态 + 有数据的状态 + 手机视口 + 深浅两主题。
有 `?state=` 之类的状态参数就一并截全。

### 步骤 4：分批改

**一批改一个主题，改完就重新截图。** 一次改二十处，出问题时你分不清是哪处引起的。

| 批次 | 改什么 | 风险 |
| --- | --- | --- |
| 1 可读性 | 对比度、焦点环、字号行高 | 零风险，先做 |
| 2 布局 | 横向溢出、列宽、密度 | 中等 |
| 3 层级 | 视觉权重、减法 | 需要看图判断 |
| 4 动效 | 状态反馈、过渡 | 最后做，最容易掩盖前面的问题 |

改的落点决定能不能传播，**从上往下**：

```
设计变量（--primary、间距、圆角）   ← 改一次全站生效
  ↓
共享组件样式（.btn、.tag、.stat-card） ← 改一次多页生效
  ↓
页面级样式（#panelCron、.stats-grid） ← 只影响本页
  ↓
行内 / 具体元素                     ← 最后手段
```

新样式**集中追加在样式表末尾**并注明改了什么、为什么。不动既有规则——
你无法确定改动的调用方。

### 步骤 5：实测验证

对比度、焦点环、层叠覆盖这三类，**看代码判断不了**，必须实测：

```bash
node scripts/verify_focus.mjs <页面>       # 键盘焦点：真实 Tab 实测
node scripts/shoot.mjs <页面> --evidence   # 对比度、溢出、动效
node scripts/shoot.mjs <页面> --compare baseline/page.png   # 前后对比
```

> **实测踩过的坑，写在这一步之前**：
> - 用 `:where()` 写样式会被原有规则盖掉。特异性为 0，
>   结果是「本来有焦点环，改完反而没了」。
> - 用 `opacity` 压暗辅助文字会把文字和底色一起混算，对比度反而掉到标准以下
>   （实测 3.55:1）。直接指定达标色值，而且要按实际底色算——
>   同一色压在白卡上达标，压在斑马纹上可能不达标。
> - 按列序写选择器（`nth-child(5)`）会误伤其他页签的表格。
>   用 `first-child`/`last-child` 或语义类名。
> - `:focus-visible` 只在真实键盘导航时匹配，用 `element.focus()` 验证会得到
>   **不稳定且错误**的结果。必须用 `verify_focus.mjs`。

### 步骤 6：交付说明

`DELIVERY.md` 要回答：改了哪些文件、基线在哪、**查了规则库的哪几条及命中情况**、
做了哪些取舍、**哪些没验证及原因**、发现了但没改的问题及原因。

「未在真实环境验证交互」比含糊的「已优化」有价值得多。

## 三、创建新项目

### 步骤 1：认品类，拆标杆

风格从品类里推出来，不从默认模板里长出来。三步，每步都写下来：

1. **说出品类和标杆。** 这是什么品类，这个品类里风格最鲜明的两三家是谁
   （选最鲜明的，不一定是最有名的）。
2. **拿到真实画面再拆。** 用浏览器或搜索取到其中两家的首屏和一个关键控件，
   **对着图拆，不凭记忆**——记忆里的产品常常是它几年前的样子。
   拆成 6–10 条看得见的要素，每条写「它是什么样 + 为什么这样做」。
   拿不到画面就在方向卡写明「未看图，凭记忆」。
3. **决定留什么、换什么。** 逐条对照本产品的受众和场合：理由成立的留下，
   不成立的换掉。

拆的时候分清：**基线**（用户已期待的结构，沿用）、**套路**（人人都在用的
默认版式，一轮里至少打破一个）、**撞脸**（字体配色主视觉都和某标杆一样，
只换了名字——任何方向都不允许）。

### 步骤 2：定三个方向

**这一步不能省，也不能合成一个。** 每个方向一个 HTML、一个视口、
只有主状态；共用同一份示例文字，结构和样式各写各的，
**不用同一个模板换几组 CSS 生成**。

四项差异检验：首屏骨架、字体、色彩、主视觉里，任意两项至多一项相同，
否则就是同一方向的变体。

| 方向 | concept（北极星） | typography | traits |
| --- | --- | --- | --- |
| A | 一句能指导取舍的体验意图 | 实际使用的字族、字重、尺度关系 | 看得见的特征 |
| B | | | |
| C | | | |

### 步骤 3：组装对比页，让用户挑

在任务目录放 `manifest.json` 和候选文件：

```json
{
  "schemaVersion": 1,
  "lang": "zh",
  "project": "项目名",
  "brief": "所有候选共同的内容与任务",
  "round": "01",
  "candidates": [
    {
      "id": "a",
      "name": "方向名",
      "concept": "北极星：一句体验意图",
      "typography": "无衬线 UI 字族，标题 32/正文 15",
      "palette": ["#112233", "#f5f5f5", "#3b62c4"],
      "traits": ["高信息密度", "状态驱动"],
      "kind": "html",
      "source": "candidates/a.html"
    }
  ]
}
```

约束（踩过才知道）：`concept`/`typography`/`traits` 必填，
HTML 候选必须是**带完整 `<head>`** 的文档，不能只有空挂载节点。
写错时生成器会一次列出所有要改的地方，且不会动旧产物。

```bash
python scripts/build_explorer.py <任务目录>/manifest.json --output <任务目录>/style-explorer.html
```

`kind` 三选一：`html`（单文件，CSS 内联）、`url`（本机开发服务器，
实时运行，只能 localhost）、`image`（截图兜底）。自写小样加
`"interactive": true` 可在对比页里直接操作。

**生成后交给用户，这轮到此结束。** 不自己挑、不接着往下做。

### 步骤 4：选定后建结构

按问题读对应文件，不要预先加载全部：

| 要解决的问题 | 读 |
| --- | --- |
| 视觉层级、字体、色彩、空间、图标、减法 | [视觉语言](visual-language.md) |
| 后台布局、状态区、表格、密度、移动端降级 | [工作区布局](workspace-layout.md) |
| 控件六态、加载/空/错、危险操作确认、动效时长 | [交互与状态](interaction-states.md) |
| 表单分组、校验时机、错误位置、提交反馈 | [表单](forms.md) |
| 断点、视口、精准还原 | [布局与视口](layout-and-viewport.md) |
| 落地页首屏骨架 | [说服型骨架](direction-persuasion.md) |
| 落地页区块出场与滑动叙事 | [滚动叙事](scroll-narrative.md) |
| 小游戏、手感、状态检查 | [游玩](play.md) |

**静态好看不等于能用。** 凡是可点的控件都要走一遍六态，
有输入的地方都走一遍表单。新界面按 [动效](motion.md) 做出三处基本动效；
落地页类页面还必须读滚动叙事。

生成设计系统 token 时可以查配色和字体：

```bash
python scripts/search.py "<品类>" --domain color
python scripts/search.py "<气质>" --domain typography
python scripts/search.py "ops console" --design-system --density 8 -p "Ops"
python scripts/search.py "rounded modal" --stack shadcn
```

`--density 8–10` 适合后台与仪表盘，`1–3` 适合落地页。
`--persist --output-dir <项目根>` 可把设计系统落盘复用。

### 步骤 5：验证与评审

```bash
node scripts/shoot.mjs <页面> --evidence --states idle,done --out evidence/
node scripts/verify_focus.mjs <页面>
```

`--evidence` 一次取齐状态图、并排图、遮字图、2 倍图、动效探测和录屏。
**只在送评审前和交付前用**，平时改完一批截一张就够。

截图工具每次会列出「默认做法提示」：可读性几项（对比度、正文字号、行高、
停在透明）**要改**；眉标、单侧色条、卡片套卡片、渐变文字这类模型默认做法，
改掉或在交付说明里逐条写出理由。

按改动范围决定是否派独立评审：

| 改动 | 评审 |
| --- | --- |
| 方向探索的对比页 | 先交给用户，不派评审 |
| 新界面、整体改版，定方向后 | 初版稳定时评审，10 分制 |
| 已有界面润色一整页以上 | 「存量已有界面润色评审」，一轮，不打分 |
| 小改动、局部低风险 | 自己看，不派评审者 |

### 步骤 6：交付说明

写清：选定的方向和理由；改了什么、哪些没做及为什么；**查了规则库的哪几条、
命中没有**；评审了几轮及方式；删掉了哪些文字；证据文件在任务目录的哪里。

另做一次减法：**每一屏只有一个主角，其余安静**；逐区块删一轮文字，
只放回删了会影响理解的。对象名称、判断依据、当前状态和主动作必须留下。

## 四、两条路都要做的减法

不管新项目还是存量项目，交付前都单独做一次：

- 每一屏只有一个主角，其余安静。
- 逐区块删一轮文字，只放回删了会影响理解的部分。
- 对象名称、判断依据、当前状态、主动作这四项必须留下。

## 五、常见问题

**Q：规则库和我的判断冲突，听谁的？**
仓库规范和用户要求优先。规则是建议不是命令。

**Q：查不到想要的规则怎么办？**
换更窄的词重查一次；仍为空就明说「规则库无匹配」，
再退回通用默认值并标注这是默认值。

**Q：截图保存成功了，但好像没真的看过？**
「保存成功」不等于「看过」。送评审前和交付前用 `--evidence` 一次取齐。

**Q：项目跑不起来怎么办？**
转静态分析路线，把能做的做了，并在交付说明里逐条写明没验证什么。
不要假装改好了，也不要为了能跑去改项目配置。

**Q：截图工具和规则库误报了怎么办？**
在交付说明里写一句。不假装通过，也不为了让检查变绿去改不该改的东西。
